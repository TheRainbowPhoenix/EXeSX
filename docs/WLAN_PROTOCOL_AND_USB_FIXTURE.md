# DY357 WLAN reply contract and future USB fixture (2026-10-29)

**Purpose:** exact original A7 code expectations *before* writing a Wi-Fi simulator. We accept the owner's hardware identification: DY357 uses **Microchip ATWINC1510**, as does DY890. The original software itself proves LPSPI2 is in its WLAN driver. We must still measure PCS/IRQ/reset pin routing and the required HIF/firmware revision.

**Sources:** owner-local `XD-SX9850.0.c` (not committed) cross-checked against the original executable data table in `a7-bios-os.elf` (also kept private); the published Microchip WINC15x0 SPI/HIF documentation; original factory run. All function names below are *Ghidra's autogenerated names*, not claimed Casio source symbols.

## A. Two different tests, do not conflate them

### TEST MENU row 8: `FUN_60059404` (factory WIFI AUTO TEST)

This is a **host-facing communication-fixture protocol**. First it prints `##### WIFI AUTO TEST #####`, then calls:

- `FUN_600597a0` -> `FUN_601770d8` (reset link state) -> `FUN_60177124(1)` -> `FUN_60177130(30000)`. The latter calls `FUN_60077848`: open external communication, wait for a connection or timeout. `FUN_60077848` logs `waiting connect`, then `CONNECTED!!`, `LINKLOST`, or `TIMEOUT`.
- `FUN_60059808` waits for an RTOS event (`FUN_600066ec(...,30000)`), requires `FUN_60177048(0)` to indicate a live cable/link, checks `FUN_60177388()` for buffered RX, and calls `FUN_60059a00` to receive **exactly six bytes**. Missing data -> `TIMEOUT!`; missing cable -> original typo `CHACK USB CABLE!`; invalid header -> `HEADER READ ERROR!`; unknown command -> `UNKNOWN CMD!`; handler error -> `RESPONSE ERROR!`.
- It dispatches on byte offset **2** using an actual six-entry ROM table, **verified independently from the original ELF at `0x6017422C`**.
- A successfully processed **command 2** causes `FUN_6000fcc4(0x32)` and exits the handler loop. `FUN_60059404` calls `FUN_60011334` on this success path, or prints `Please Press 'ENTER' Key.` on failure.

### The six-byte communication frame

`magic[2] | command[1] | argument[1] | length[2] | payload[length-6]`.

The first two bytes are `FF FF`. The *received* `length` is read as a native A7 `short` in `FUN_60059808`, apparently **little-endian**. The A7 uses `length - 6` to determine the body byte count for handlers. It requires six complete header bytes: a short header is rejected (`FUN_60059a00` checks the byte count). The reply constructors usually use a status byte `80`, `81` or `82` at offset 2.

**Unresolved endian quirk:** `FUN_6005a134` builds some outgoing replies as bytes `FF FF 80 05 00 40` and transmits 64 bytes; interpreting `00 40` as a native little-endian length would give 16384. We should capture real USB/fixture traffic **before claiming a uniform length endian rule**; the included decoder reports both candidates. We must not silently "fix" the original bytes.

| Command byte | Original handler | Verified purpose |
|---|---|---|
| `01` | `FUN_60059a34` | Sends six-byte response `FF FF 80 00 06 00` |
| `02` | `FUN_60059a70` | Shuts down WLAN service if initialized; sends six-byte response, then **completes** factory command loop |
| `03` | `FUN_60059ab8(arg, length-6)` | Receives full requested payload; `arg` subcommands 1 init, 2 connect AP, 3 disconnect, 4 socket server flow, 5 socket/client/data flow; sends status `80` or `82` for supported requests, `81` for unknown |
| `04` | `FUN_6005a134(arg)` | Query subcommands 1 AP SSID/channel, 2 MAC + companion fields, 3 RSSI summary, 4 current connection information, 5 IP configuration; some query responses include variable data |
| `05` | `FUN_6005a5d8` | Original sends six-byte unsupported status `81` |
| `06` | `FUN_6005a618` | Original sends six-byte unsupported status `81` |

**This protocol runs over the factory communication link, not directly over ATWINC1510 SPI.** An external host/fixture *sends* command 1/3/4/2 and reads back the results. The modem is used **inside** command handlers. A virtual WINC card alone cannot advance this factory loop; a second, later USB-device/fixture emulator is needed.

Read-only frame analyzer: `python3 scripts/decode_dy357_factory_wifi.py 'ff ff 03 01 06 00'`. This parses captured bytes only, and **does not** inject any guest event or assert a factory PASS.

## B. WLAN CHECK MENU: actual ATWINC1510 host replies

The original `FUN_60068DDC` submenu contains COMMUNICATION, BATTERY LIFE, POWER SAVE MODE, FIRMWARE, and MAC ADDRESS. It dispatches to `FUN_601cdc44`, `FUN_601cdc80`, `FUN_601cdcc0`, `FUN_601cdd00` and `FUN_601cdd40`. Its next level is a different protocol from factory command IDs above.

| Native test | A7 call and awaited condition |
|---|---|
| WLAN init | `FUN_601cfb14` calls `FUN_601ca0e0` (SPI + WINC HIF startup), then `FUN_601c40b4` for a configured radio option; failure gives `WLAN INIT ERROR!` |
| RSSI | `FUN_601cdd80` -> init -> `thunk_FUN_601ca3d4` to connect to configured SSID/password -> wait via `FUN_601cdaf8(6,...)` on asynchronous A7 type `0x400` callback. Then `thunk_FUN_601ca8b8` supplies SSID/channel and `FUN_601cfbb4` supplies current/max/min/average RSSI; errors `WLAN CONNECT ERROR!`, `NG: GET AP STATE ERROR!`, `NG: GET RSSI ERROR!` |
| Firmware version | `FUN_601cf53c` -> init -> `thunk_FUN_601ca7d0(buf,20)` -> version info request / version formatting (`x.y.z`); success displays `OK: FIRMWARE VERSION %s`, failure displays `NG: VERSION CHECK ERROR!` |
| MAC address | `FUN_601cf678` -> init -> `thunk_FUN_601ca83c(buf,6)` -> `FUN_601c3f98`; success requires a six-byte result and displays `OK: MAC ADDRESS %02X:...`. Failure gives `NG: MAC ADDRESS ERROR!` |
| Power save | `FUN_601cf31c` requests automatic deep sleep and an AP connect, or `FUN_601cf448` powers down/wakes and measures elapsed time; an immediate generic success byte does not satisfy the original waits |
| TCP/iperf | `FUN_601cdfd0` creates/binds/connects a socket and sends data after WLAN initialization, AP association and an external TCP server fixture. Need asynchronous socket events and real host network test setup |

**Observed original A7 HIF messages:** `FUN_601c0708(group, opcode, header, header_len, ...)` constructs an **eight-byte** HIF header: group, opcode, total length, and additional metadata. Length is bounded at `0x63C` bytes. It uses WINC host registers `0x108C`, `0x1078`, `0x150400`, `0x106C` to announce request DMA buffers. `FUN_601c0970` consumes pending interrupt/status at `0x1070` and reads an incoming message pointer from `0x1084`. These are **WINC internal register addresses** accessed via its SPI protocol, not i.MX7ULP MMIO addresses.

In the original WINC callback dispatcher `FUN_601c9c4c`, message/opcode `0x2C` changes Wi-Fi connection state, `0x2F` updates AP/SSID information, `0x32` marks another connection or initialization response, `0x11/0x13` fill the scan results, and `0x04/0x06` record other status. These update the real OS flags and lead to A7 type-`0x400` event IDs; `FUN_601cdaf8` observes those event IDs. **Do not create artificial A7 events**: the SPI device must return proper DMA/HIF frames and IRQ so the *original* handler produces them.

## C. Proven LPSPI2 traffic shape and missing emulator behavior

The original WLAN module uses `0x40290000` (LPSPI2):

- `FUN_601c2e3c` initializes LPSPI2 and writes `DER=0` at `0x4029001C`.
- `FUN_601c2248/228C/22A8` reset FIFOs, enable controller, program `CFGR1=3` and FIFO watermarks.
- `FUN_601c2580` (transfers **under 61 bytes**) sets `TCR` frame bit length to `bytes * 8 - 1`, **packs up to 4 bytes per 32-bit `TDR` write**, waits on `FSR.RXCOUNT`, reads packed words from `RDR`.
- `FUN_601c2740` (**61..8192 bytes**) uses DMA0 descriptors to and from `TDR/RDR`, transfers in 512-byte chunks, and waits for original RTOS flag `0x16:1` with timeout 5000.

This is decisive: the current opt-in 8-bit PIO model is only an initial negative-control. It **cannot run the actual WINC host driver** because the real guest often asks for multi-byte `TCR` frames and DMA completion.

### Suggested Python/WINC device boundary

```text
Original A7/M4 -> real LPSPI2 MMIO + DMA + NVIC
                 -> C QEMU SPI master (frame packing, PCS, status, FIFO)
                 -> byte-stream device bridge (Unix socket or localhost TCP)
                 -> Python WINC1510 SPI-slave model
                    -> register space + SRAM + flash image
                    -> HIF request/response queues and IRQ_N/WAKE/RESET_N
                    -> optional controlled AP/socket backend
```

The C side must own clock/PCS/transmit/receive and DMA side effects. Python receives **bounded complete transactions** (`BEGIN{bus,pcs,mode}`, `XFER{tx_bytes}`, `END`), and returns equal-length `rx_bytes` and pending `irq_n` state. It may asynchronously post events through an event queue; guest interrupts must be asserted by the QEMU GPIO/IRQ model, not by guest memory patches. A socket disconnect leaves the card absent/unavailable, never silently "connected".

Microchip WINC hardware SPI opcodes are `C1` DMA write, `C2` DMA read, `C3/C4` internal register write/read, `C7/C8` extended DMA, `C9/CA` single register write/read; command CRC, command-echo acknowledgement, internal register map and DMA FIFOs must match actual Microchip driver and a captured original transaction. A simple Python "return chip ID" is only a first probe.

The host implementation and Python device should provide **both real negative controls and explicit fixture configuration**, including no-radio, wrong chip, absent AP and missing fixture behavior. Until this model is running, no WLAN factory `OK` is proven.

## D. USB cable: separate future emulation, with exact ROM hooks

The original `FUN_60038FB0(1)` calls `FUN_6003900C`, which checks **GPIOB.PDIR bit 19** at `0x4100F050 & 0x00080000` for an input sense; it mirrors the result to shared `0x2F029219`. `FUN_6003902C` also examines `0x40350808` (inside the i.MX7ULP USBPHY register window) and sets an RTOS event. This is a **physical cable/PHY status lead**, not a license to force it high.

The SoC exposes USB OTG at `0x40330000`, USB miscellaneous control at `0x40330200`, and USBPHY at `0x40350000` in the upstream Linux i.MX7ULP device tree. The specific meaning of the original bitfields in `0x40350808` still needs reconciliation with the NXP USBPHY reference manual.

In `FUN_60077848` the original opens the communication interface, registers its callback, and waits for a connection; link state is held in `0x625EE030` (with `0` open, `2` closed, `0xFFFFFFFF` uninitialized among observed cases). Read and write use distinct `0x2000`-byte circular buffers and send data to the USB driver through RTOS flags. Any future USB device controller must implement enumeration/endpoint traffic, cable status, DMA/buffers and correct event delivery before the external Python factory **fixture** can send the six-byte commands from section A.

This suggests **two independent Python processes** are possible: WINC1510 SPI slave for WLAN CHECK; USB test fixture attached to the emulated Casio USB controller for factory WIFI AUTO TEST. Emulating only the first will not make the second pass.

## E. Firmware extraction and possible real execution

A **read-only firmware dump is technically feasible**: Microchip documents an 8 **Mbit** internal serial flash in ATWINC1510 (about **1 MiB**). Their WINC programmer utility supports reading the entire flash (`-r`) via supported hardware interfaces. The flash can also be read through the host bus with the WINC processor halted to avoid conflicts. Its contents can include private network profiles and MAC/device configuration; never publish a raw dump.

Additionally, the original DY357 **host OS** contains `FUN_601ca1d8` and `FUN_601c7174`, which open **`\\data0\\sys_bin\\ota.bin`** and write **0x3B000 bytes** (241,664 bytes) to the device starting at **flash offset 0xA000** in 4 KiB blocks. This is evidence of a possible owner-OS-supplied WLAN update image, **not** proof that that file is present in the available sparse eMMC nor that it contains the full card firmware. Look for it in a legitimately obtained `data0` image.

Running dumped firmware directly is considerably harder than simulating its protocol: Microchip documents an **APS3S-Cortus 32-bit CPU at 40 MHz**, **not ARM**; it also needs WINC RAM, timers, interrupt controller, SPI flash, DMA/MAC/RF peripherals and boot behavior. Standard QEMU ARM execution cannot load and run this CPU's instructions. Recommended near-term plan: **protocol/HIF Python simulator** first; actual Cortus firmware execution as a separate long-term emulator effort.
