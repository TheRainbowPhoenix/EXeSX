# XD-SX9850 firmware progress — M4 I²C2 and ADC0 (2026-10-20)

## Observed execution (private OSUP.BIN, never committed)

Rebuilt the A7 ELF using the checked-in `scripts/prepare_osup.py`.
The actual firmware starts the Cortex-A7 and then releases the Cortex-M4
at its copied vector table (M4 MSP 0x20001C00, PC 0x1FFE19E5).

With `EXESX_EXPERIMENTAL_M4_BOOT=1` and the pinned native development
build `a4c644563a3d3fe9cde6ad2a4d023b497fe8cf4e`, the M4
repeatedly attempts transfers on **LPI2C2 at 0x41035000**:

- MTDR `0x0496`: START, 8-bit I²C address byte 0x96 = **7-bit slave 0x4B, WRITE**
- MTDR data bytes `0x14`, `0x62` (appears to use a 16-bit register address 0x6214)
- MTDR `0x0497`: START, 7-bit slave 0x4B, READ
- No physical slave is modeled by default: the controller appropriately returns NACK.

This is **not enough to identify the external chip**. Candidate I²C sensors and
power ICs share addresses; neither successful probing nor a chosen data value
would establish hardware identity.

A clearly diagnostic and opt-in parameter `EXESX_I2C4B_REPLY_HEX` already exists
in EXeSX's LPI2C model. It is NOT enabled by default. In separate 1.25-second
firmware runs with response bytes `00`, `55`, `ff`, and `ab12`, **00 and FF**
altered real M4 execution sufficiently to reach a further Data Abort:

```text
Taking exception 4 [Data Abort] on CPU 1
...at fault address 0x41041010
...with CFSR.PRECISERR and BFAR 0x41041010
```

Other values continued repeating I²C transactions. This is differential evidence
of a software dependency, not proof that the real external chip returns 00 or FF.

## New fault identified: ADC0 CTRL

The NXP i.MX7ULP device's official CMSIS common header defines
`ADC0_BASE = 0x41041000`, and `PERI_ADC.h` identifies `+0x10` as
**ADC_CTRL**. It also defines ADC0/ADC1 `CTRL/STAT/CFG/FCTRL/SWTRIG`,
trigger-control registers at `0xC0/0xC4`, 15 command entries
`0x100..0x174`, comparison registers `0x200..0x20c`, and
result FIFO at `0x300`.

New module `hw/arm/exesx-imx7ulp-adc.inc` models those documented
registers and ordinary configuration. Reset and reset-FIFO strobes
self-clear, status W1C clears bits, the result FIFO is empty when there
is **no analog source**, and software triggers are logged without
inventing conversion results. ADC0 at `0x41041000` and ADC1 at
`0x410ad000` are enabled by `profiles/imx7ulp-early-boot.ini`.
`scripts/probe_adc.py` executes real Cortex-A7 ARM code to verify
CTRL reset, CFG readback, FCTRL hardware-owned count, empty FIFO and
software-trigger clearing.

## Reproducibility after workspace or container reset

The repository **already contains** `scripts/recover_exesx.py`, which
accepts `OSUP.BIN` or `OSUPD.bin`, validates its checksum, downloads the
published native emulator with SHA256 validation, extracts private BIOS/OS
locally, and executes a bounded dual-core run. For example:

```bash
python3 scripts/recover_exesx.py /path/to/OSUP.BIN \
  --workdir ./exesx-recovered --seconds 2
```

`--mode local` and `--qemu` support an already-downloaded release
without any network request. The recovery script was smoke-tested from the
packaged native release against the supplied user firmware on 2026-10-20.
The private ELF and logs remain in the local recovery working directory.

## Measured outcome after ADC0/ADC1 model

CI run [39442236778](https://github.com/TheRainbowPhoenix/EXeSX/actions/runs/39442236778)
completed successfully, including `scripts/probe_adc.py` executing real ARM
instructions. Tested build SHA: `3ab9801bfa3d4df7f2298ec5bbdcc364452036bc`.

Using the **real extracted Casio firmware**, enabling the explicitly artificial
slave reply of either `00` or `ff` now causes the M4 to execute *six*
previously inaccessible ADC reset/control writes:

```text
ADC0 +0x10: 0x00000002 ; 0x00000000 ; 0x00000100
ADC1 +0x10: 0x00000002 ; 0x00000000 ; 0x00000100
```

The prior M4 BusFault at `0x41041010` is absent in both tests.

The CPU/IPC monitor on the same tested QEMU image distinguishes:

| I2C condition | M4 IPC word at 0x2F028000 | A7 observed PC |
| --- | --- | --- |
| No slave, proper NACK | `0x00000000` | `0x601BA02C` (wait/poll path) |
| Opt-in artificial `00` reply | `0xEEEEEEEE` | `0x60179A7C` (holding loop) |
| Opt-in artificial `ff` reply | `0xEEEEEEEE` | `0x60179A7C` (holding loop) |

The M4 reached more firmware routines following ADC initialization; after
ADC0/1 was implemented, there were **no Data Aborts in either run**.
The A7 holding loop is an explicit ARM `B .` instruction and **is not a
working RTOS or home screen**. `0xEEEEEEEE` is an observed mailbox value;
its exact *semantic meaning* has not been proven by hardware yet.
The test value is from an artificial responder, not proof of any chip output.

### Strong candidate for 0x4B: Atmel/Microchip maXTouch

This new public-source hypothesis is supported by two independent matches:

1. maXTouch application addresses can be either **0x4A or 0x4B**.
2. maXTouch memory operations write the **least significant register address
   byte first**, then the most significant. The firmware emits MTDR
   `0x0014,0x0062` after a START to 0x4B, consistent with a pointer
   to `0x6214`.

Sources:
- [Microchip MXTAN0213 maXTouch I2C application note](https://ww1.microchip.com/downloads/en/Appnotes/MXTAN0213_Interfacing_with_maXTouch_Touchscreen_Controllers_00002428A.pdf)
- [Microchip mXT1664T3 datasheet, I2C interface and register-pointer order](https://www.alldatasheet.com/html-pdf/1244818/MICROCHIP/MXT1664T3-MABRQTP/19815/34/MXT1664T3-MABRQTP.html)
- [Linux in-tree Atmel maXTouch touchscreen driver](https://github.com/torvalds/linux/blob/master/drivers/input/touchscreen/atmel_mxt_ts.c)
- [Linux maXTouch platform definition, with both device addresses](https://android.googlesource.com/kernel/msm/+/android-6.0.1_r0.94/include/linux/atmel_maxtouch.h)

**The Casio controller is not yet identified.** Many chip families
support 0x4B; board photos, I²C dumps, or evidence of a maXTouch
information block/object table are needed to establish the model and
actual register values. Do not substitute arbitrary `00` or `ff` as
a permanent touchscreen model.

Use the new `scripts/compare_i2c_boot.py` against a *private* ELF
to replicate these checks with independent cold runs:

```sh
python3 scripts/compare_i2c_boot.py private/a7-firmware.elf \
  --qemu build/qemu-system-arm \
  --profile profiles/imx7ulp-early-boot.ini \
  --cases none,00,ff --seconds 0.8
```

This emits `comparison.json`, both CPU PCs and the live IPC word, with
separate logs for each test. It does not require rebuilding QEMU.
