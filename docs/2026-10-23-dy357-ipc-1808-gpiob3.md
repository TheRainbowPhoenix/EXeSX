# DY357 post-DMA service 0x1808: original A7↔M4 GPIOB3 response

**Date: 23 October 2026.** Original private owner-held OSUP SHA256
`d5791bec1c7739315fb6113b5d6890a21f6c454fcf7a05a0381cfaaa70808fb0`.
Tested the same unchanged extracted A7 ELF and source-derived, incomplete
synthetic eMMC with the **previously passing QEMU 10.1.0 EXeSX native artifact**,
opt-in DMA1/LPIT1/MU/M4/LCD. No firmware, raw GDB dumps, screenshots or
synthetic media are uploaded to GitHub.

## Original A7 request and original M4 producer (now dynamically verified)

The original A7 at `0x600488A0` calls `0x6001EC14`, which submits service ID
`0x1808` to the generic A7 dispatcher at `0x6017807C`.
The dispatcher uses a 72-byte shared IPC slot at `0x2F028000`.
For the observed slot index **0**, the original A7 writes the request ID to
`0x2F02800C`, publishes it and waits for a response. No speculative or
fake reply is injected.

Actual GDB stop on the **shared response word write watchpoint**
`Z2,2f02800c,4`, armed only *after* A7 request publication
`0x60178048`, stops on **thread 2, Cortex-M4**, at `0x1FFDC784`.
The **live guest Thumb code** at that PC is a store of the M4 helper return
(`R0`) into the shared response word, after `BL 0x1FFDBCDE`.
The M4 then publishes the response-complete slot state. A7
`0x60178054` copies the response; `0x6017807C` returns
transport status **0**, while `0x6001EC14` yields application result
**1 or 0** from the copied response word. These are distinct statuses.

**Important binary-layout finding:** the live M4 Thumb code in RAM at
`0x1FFDBCDE` is **not** the original bytes at the same address in the
container's IPL image. The live bytes match a source region of the validated
OSUP at raw offset `0x001F957E`; firmware has copied/relocated code.
The private guest-memory Thumb disassembly, not IPL-at-address disassembly,
establishes this instruction chain.

## What original M4 helper 0x1FFDBCDE actually checks

The M4 helper loads the literal hardware register address
**`0x4100F050`**, M4 **GPIOB.PDIR**, and samples **bit 3** five
times. For each sample where the input bit is **LOW**, it increments a
counter. When all five samples are LOW, it returns **R0=1**.
Otherwise, the path returns **R0=0**. That result is what the A7 receives
for service `0x1808`.

This is a concrete original-firmware consumer of an externally driven GPIO.
The project previously used opt-in
`EXESX_GPIOB_INPUT_MASK=0x80` to hold **GPIOB7 HIGH** for an earlier
M4 boot-permission condition, leaving GPIOB3 LOW. The correct *physical*
GPIOB3 default voltage and board wiring remain unverified.

### Controlled GPIO input differential, no original code altered

Using identical original ROM, QEMU build, and source-only synthetic eMMC,
only the diagnostic GPIOB mask was changed:

| Original-firmware breakpoint / observation | Diagnostic mask `0x80` | Diagnostic mask `0x88` |
| --- | --- | --- |
| A7 request `0x6001EC44` / ID | `0x1808` | `0x1808` |
| M4 write-watchpoint / PC | thread 2 / `0x1FFDC784` | thread 2 / `0x1FFDC784` |
| M4 register R0 when writing response | **1** | **0** |
| A7 service result at `0x600488A4` | **1** (retry) | **0** (exit inner wait) |
| A7 outer retry decision `0x60048924` | **R0=1** | **R0=0** |
| A7 successful exit `0x60048934` | Not observed during bounded test | **Observed, R0=1 for next service** |
| OS `0x60400000` / visible text | Not observed | Not observed |

This **demonstrates causality for the 0x1808 retry** within the
experimental diagnostic GPIO model. It does **not** authenticate a real
GPIOB3 pull-up or establish that the original OS boots afterward.
Subsequent A7 monitor snapshots still land in BIOS WFI at
`0x601CBCF8`, which may be normal scheduler idle.

## Remaining high-LBA storage dependency is separate

Both branches of the GPIO experiment still issue substantial eMMC user-area
CMD18 reads beyond source-provided update bytes, including
`0x008A3705` in the baseline trace; the source-only sparse emulated
medium has **zero/unknown contents** there.
A command trace or zero backing alone **does not prove** that missing
installed eMMC contents caused this `0x1808` result: the M4 GPIOB3
input is now the actual measured producer. Missing installed storage
and later callback dispatch remain independent open dependencies.

## Reproduction, tests and code

```bash
# Previous opt-in GPIOB7 high only (B3 low)
python3 scripts/run_osup.py /private/OSUP.BIN --dma1-m2m \
    --ipc1808-probe --seconds 35 --output-dir private/ipc-low

# Same firmware/model, plus *experimental* B3 high (no physical claim)
python3 scripts/run_osup.py /private/OSUP.BIN --dma1-m2m \
    --gpiob3-high --ipc1808-probe --seconds 35 \
    --output-dir private/ipc-high
```

The new `scripts/probe_ipc_1808.py` records only private GDB metadata:
request ID, allocated shared slot, original A7 caller and M4
response-writer thread/PC, result and selected register state.
It installs a response-word GDB **write watchpoint after request
publication**, avoiding the false-positive original A7 request write.
No guest RAM registers are overwritten and no IRQ/OS callback is forced.
Synthetic tests check the stride/bounds and thread-stop decoding; existing
firmware-free GPIO input regressions remain in place.

## First downstream barrier after successful GPIOB3 response

A separate unchanged-ROM, `0x88` high-input read-only GDB run reached the normal BIOS service exit
`0x60048934` and caller return `0x60048E08`. Its next service
`0x6001EDA8` returned **`R0=0xCA05`** at `0x60048E0C`. Original ARM compares
this value against literal `0xCA05` and, when equal, calls
`0x60010868` at `0x60048E18`.

A new bounded run actually entered `0x60010868`, reached its
call `0x6001D524` at `0x60010894`, and reached the return comparison
`0x60010898` with **R0=1**. Disassembly shows that nonzero here goes
back through a firmware-requested 125-unit delay and polls again.
The routine also has a separate data/queue path at
`0x600108A8`; it was not observed in the bounded first-result
breakpoint sequence. No return to the outer startup call
`0x6004A2B0` or OS trampoline was observed.

**Next current open dependency:** determine the producer/semantics of
`0x6001D524`'s nonzero result or its underlying queue/device and
validate a real return from `0x60010868`. This may be a temporary
nonzero service condition rather than a permanent stall: the original
run is time bounded, and an idle CPU snapshot does not prove the
service never recovers. This later gate must not be conflated with
the **resolved GPIOB3-driven 0x1808 response**.

## Independent 23 October native QEMU confirmation and CI repair

The attached original OSUP was checksum-verified again (`SHA256 d5791bec1c7739315fb6113b5d6890a21f6c454fcf7a05a0381cfaaa70808fb0`) and its unchanged A7 BIOS/OS was loaded in the pinned native QEMU 10.1.0 artifact. Synthetic media held checksum-valid PVOS at boot1 LBA0/32 and only source-available user B/A/F bytes. A bounded direct A7 GDB test, CPU0 selected, with **experimental** `EXESX_GPIOB_INPUT_MASK=0x88`, observed these live breakpoints:

```text
CPU0 PC=0x6001EC44  R1=0x00001808  genuine service request
CPU0 PC=0x600488A4  R0=0x00000000  original request result
CPU0 later sampled at BIOS idle 0x601CBCF8
```

This is a **second independent read-only QEMU confirmation of high-B3 response zero**, matching the earlier controlled M4 thread-2 watchpoint and A7 0x80-versus-0x88 differential. A fresh follow-up low-B3 local probe timed out before collecting its breakpoint evidence, so do **not** use that failed attempt as a new low-B3 observation; the preceding controlled 0x80 data remain the documented low-input evidence. No new OS entry or glyph claim.

Static cross-check of the original ROM's **relocated** M4 helper: validated OSUP raw offset `0x001F957E` maps to live M4 Thumb entry `0x1FFDBCDE`. The Thumb instructions increment a counter on each GPIOB bit3 LOW sample, loop exactly five times (`CMP R0,#5`), compare LOW count with five, and select R0=1 versus R0=0 accordingly. Its `LDR.W` literal at M4 `0x1FFDBCF0` resolves to original source offset `0x001F9EA0`, whose value is **0x4100F050** (GPIOB.PDIR). This separately confirms the predicate without importing firmware bytes into GitHub.

CI follow-up: latest complete native QEMU workflow [39927232405](https://github.com/TheRainbowPhoenix/EXeSX/actions/runs/39927232405) **passed** after repairing the accidentally literal `\\n` in `scripts/probe_gpiob_input.py` and escaped GDB diagnostic shell continuations. The synthetic-ARM `EXESX_GPIOB_INPUT_MASK` tests also passed locally against the earlier pinned QEMU artifact: masks `0`, `0x80`, `0x88` yielded PDIR triples `[0,0x80,0]`, `[0x80,0x80,0]`, and `[0x88,0x88,0x08]` respectively. The public native build/test remains free of proprietary firmware.

The remaining BIOS-to-OS gate is separate: with GPIOB3 high, the subsequent `0x60010868` / `0x6001D524` service returns nonzero in the previous live study. Identify its real producer and whether the later wait terminates; do not force registers or create absent eMMC sector data.
