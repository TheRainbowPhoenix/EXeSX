CURRENT EXECUTION BLOCKER: EXTERNAL I2C 7-BIT ADDRESS 0x4B
REAL M4 LPI2C2 MTDR writes (not invented):
 0x0496 START to I2C 0x4B WRITE
 0x0014 data byte
 0x0062 data byte  (possibly 16-bit little-endian pointer 0x6214)
 0x0497 repeated START to 0x4B READ
No modelled physical I2C slave: proper NACK and M4 retries.
Hypothesis: Microchip/Atmel maXTouch (possible 0x4A/0x4B address,
little-endian pointer). UNCONFIRMED. Board markings/physical bus capture
or convincing object-table response required.

Diagnostic opt-in fake I2C replies 00 and FF DO NOT BOOT:
They advance real M4 firmware through ADC0+ADC1 CTRL writes
 0x2, 0x0, 0x100 on both units; previous ADC0 abort is gone.
But they then produce shared IPC 0xEEEEEEEE and A7 PC 0x60179A7C
(a literal self-loop). The A7 comparison at 0x601786CC sends this
value to a diagnostic/error-management branch via 0x6001EE68.
With NO slave, IPC is 0 and A7 was sampled at 0x601BA02C.
These are bounded real-QEMU observations, NOT a working menu.
Source confirmed in commit 3ab9801bfa3d4df7f2298ec5bbdcc364452036bc
 https://github.com/TheRainbowPhoenix/EXeSX/actions/runs/39442236778

REBUILD FROM PRIVATE USER OSUP.BIN or OSUPD.bin
Linux x86_64 + Python 3:
 curl -fL https://raw.githubusercontent.com/TheRainbowPhoenix/EXeSX/main/scripts/recover_exesx.py -o recover_exesx.py
 python3 recover_exesx.py /path/to/OSUP.BIN --workdir ./exesx-recovered --seconds 2
Recovery downloads/checksums the firmware-FREE native QEMU release;
locally validates/extracts the user's ROM into private/a7-firmware.elf;
runs experimental dual-core QEMU; saves results/latest logs.
 --mode source builds from source; --mode local --qemu /path/to/qemu
works with an existing QEMU binary. DO NOT PUBLISH extracted ROM.

RAW FIRMWARE RUN
 EXESX_EXPERIMENTAL_M4_BOOT=1 python3 scripts/run_firmware.py private/a7-firmware.elf --qemu build/qemu-system-arm --profile profiles/imx7ulp-early-boot.ini --seconds 2
Tracked CPU context, IPC, source SHA and I2C test input matter.
