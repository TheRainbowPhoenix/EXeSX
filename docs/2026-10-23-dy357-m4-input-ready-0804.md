# Original DY357 140-second boot and M4 service 0x0804 input-ready gate

23 October 2026. This is metadata from **unchanged private original OSUP**, SHA256
`d5791bec1c7739315fb6113b5d6890a21f6c454fcf7a05a0381cfaaa70808fb0`.
QEMU 10.1.0 was compiled from Linux CI artifact commit `3be7835`, using
source-derived synthetic eMMC, DMA1 M2M, M4/MU, LPIT1 IRQ, experimental LCD
and opt-in GPIOB pin-high mask **0x88**. No proprietary bytes, screenshot or
raw trace is committed.

## Long-run observation, not inferred from firmware static strings

An original-firmware native QEMU run completed **140 seconds bounded
wall time** with 64 recorded `sdhci_send_command` operations and
one real 829,440-byte DMA1 M2M transfer. The final LCD screenshot remained
the genuine BIOS version box: 864×480, **6046 nonwhite pixels**, nonwhite
bounding rectangle **[304,160,560,296]**. With `-d in_asm`, 6,231
newly-translated original A7 BIOS instruction addresses appeared but
**none from OS section 0x60400000...** (first-translation logging is
not a full executed-instruction trace). The final early storage
command argument was **0x0084157C**, outside source-provided updater
sectors; absence of installed flash data is **not proved the 0x0804 gate**.

A separate 75-second original-ROM GDB breakpoint run hit
`0x60048E0C R0=0xCA05`, `0x60010868` (version dialog routine),
`0x600105CC` (actually draws it), `0x60010894` (submits event query),
and `0x60010898 R0=1` (event query blocks progress). The
A7 CPU0 ended sampled at BIOS idle `0x601CBCF8`, with accepted
components status 0x3f, registered OS callback `0x60400000`,
callback cache zero and service-ready byte zero. An idle sample does
not prove permanent failure.

## Actual original M4 producer and precise GPIO predicate

Original A7 `0x6001D524` sends service **0x0804** through its real
shared 72-byte-slot dispatcher `0x6017807C`. An actual native
dual-core GDB run armed a response-word write watchpoint **after**
A7 published the request, and stopped on **M4 thread 2
PC 0x1FFD7C76**, executing `STR R0,[R4,#8]` with **R0=1**.
The A7 then read the M4's word 1 and genuinely returned
`R0=1` to `0x60010898`. This is not a transport error:
A7 dispatcher returned transport status 0.

The **relocated live M4 Thumb helper `0x1FFD7E98`**
is called by the response handler `0x1FFD7C6E`. Its constants
at live M4 0x1FFD8988/8C are:

- mask **0x808C6008**
- **0x4100F010** = M4 GPIOA.PDIR (GPIOA base 0x4100F000)

The handler samples masked **GPIOA.PDIR three times** and
returns 1 if the sampled bits differ or if not *all*
seven bits in `0x808C6008` are high. Only after those bits
are stable/high does it sample **GPIOB.PDIR at
0x4100F050** three times, masking **bit 6 (0x40)**. It
returns 0 if bit6 is stably high; 1 if stably low.
This corresponds to the firmware's nonzero=wait condition,
but exact electrical meaning and physical keyboard/board wiring
remain **unverified**.

At the actual M4 response, untouched GPIO readback was:

```text
GPIOA.PDIR=0x00000010  GPIOA.PDDR=0x00338BF5  GPIOA.PDOR=0x00000410
GPIOB.PDIR=0x00000088  GPIOB.PDDR=0x00068C04  GPIOB.PDOR=0x00000000
```

**None** of GPIOA mask 0x808C6008's bits is configured as an
output, and GPIOB bit6 is also configured as input. The
currently attached EXeSX external GPIO model assigns no voltage
to these board inputs, so it cannot satisfy the original M4
predicate. This is a specific, reversible **missing external
input-voltage model**, not the earlier 0x1808 GPIOB3 gate.

## Implementation and A/B validation plan

The new opt-in `EXESX_GPIOA_INPUT_MASK` affects **only M4
GPIOA at 0x4100F000**, never A7 GPIOA LCD D/C at
0x400F0000. An input mask is combined with the device's
existing `PDIR = (PDOR&PDDR)|(external & ~PDDR)`, so
**guest-configured outputs always win**. The existing B mask is
unchanged. Original firmware/event replies/IRQ state and
media are not patched or forced.

The private launcher accepts independent
`--gpioa-input-mask` and `--gpiob-input-mask` with
validated 32-bit values; its default remains unchanged.
Run the following controlled comparison with the **new CI QEMU
artifact**:

```bash
# Control: original DY357 candidate B7/B3 high, missing PTA and B6 inputs
python3 scripts/run_osup.py /private/OSUP.BIN --dma1-m2m \
  --gpiob3-high --seconds 90 --output-dir private/control-0804

# Research hypothesis: only external input voltages A and B6 change
python3 scripts/run_osup.py /private/OSUP.BIN --dma1-m2m \
  --gpioa-input-mask 0x808c6008 --gpiob-input-mask 0xc8 \
  --seconds 90 --output-dir private/m4-ready-0804

# Read-only A7/M4 response producer evidence, repeat with both masks
python3 scripts/run_osup.py /private/OSUP.BIN --dma1-m2m \
  --gpioa-input-mask 0x808c6008 --gpiob-input-mask 0xc8 \
  --ipc0804-probe --seconds 70 --output-dir private/probe-0804
```

The firmware's version-dialog routine `0x60010868`
falls through to keyboard/event queue `0x600108A8` only
when service 0x0804 returns zero. It reads events via
`0x60009FB0` and tests 0x93 (147), 0x94 (148),
0x80 (128) and 0x95 (149) in its diagnostic
key-sequence loop. **This is not yet a complete keyboard
input device** and not proof a main/test menu will open;
the known BIOS test menu dispatch around `0x600673D4`
and OS trampoline `0x60400000` require real execution
breakpoints before any success claims.

Both CI platforms perform firmware-free synthetic ARM GPIOA
PDIR/PDDR voltage tests, including output override. Private
owners can audit `ipc0804-summary.json` without sharing
the original ROM or raw trace.
